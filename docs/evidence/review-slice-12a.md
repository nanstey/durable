# Independent review: slice 12a (PR #53, passkey approvals)

Scope: `src/approval/webauthn.ts`, `src/approval/nonce.ts`, `/v1/approvals/*`, `/v1/resume`, `/v1/policy/*/verify` in `src/api/routes.ts` and `auth.ts`, `src/console/proxy.ts`, `web/app.js`, `src/cli/main.ts`, against `docs/plan/specs/12a-*.md`. Read-only review; PoCs ran in `/tmp` (library challenge encoding, second-key enrollment). Commit reviewed: `127b936`.

Summary: **High 5, Medium 6, Low 4.** The slice cannot work with a real authenticator, and the second-key rule is not enforced. `docs/evidence/slice-12a.md` rows "Implemented" are largely unbacked: the PR adds **no test** for `src/approval/webauthn.ts` (the only new test is one proxy header test).

## High

1. **Every real assertion/registration fails: challenge encoding mismatch.** `src/approval/webauthn.ts:166-167,208-218,223-231` stores the raw base64url `challenge` and passes the *string* to `generate*Options`; SimpleWebAuthn 14.0.3 UTF-8-encodes a string challenge, so `options.challenge` is `base64url(utf8(challenge))` (PoC: stored `abc_DEF-123`, sent `YWJjX0RFRi0xMjM`). The browser signs the sent value; `verify*Response` at `:271-275,296-302` receives the raw value as `expectedChallenge` and the library requires the base64url `options.challenge` (`verifyAuthenticationResponse.js:71`). Fix: generate `Uint8Array` bytes, or store `options.challenge` and pass that as `expectedChallenge`. Add a real fixture test.
2. **Browser serializer sends `{}`.** `web/app.js` `json(credential)` walks `Object.entries` of a `PublicKeyCredential`; `id/rawId/response/type` are prototype accessors, so no own enumerable keys exist. The assert body has an empty response and `key` lookup fails. Fix: `credential.toJSON()` (or `PublicKeyCredential.parseCreationOptionsFromJSON` / `parseRequestOptionsFromJSON` for the options side).
3. **Second key needs no existing-key assertion (spec A3).** `webauthn.ts:184-202` checks the code only when `state.keys.length === 0`; with keys present, `options("enroll")` issues a registration challenge to any caller of the unauthenticated `POST /v1/approvals/challenge` (`auth.ts:37-58` bypasses bearer auth; `routes.ts` passes the action through). Then `verifyEnrollment` `:293-316` adds the key. PoC: with one key stored, `options("enroll")` returned a challenge without any assertion. Anyone who reaches the daemon (tailnet peer, local process) can enroll their own passkey and then approve merges, release holds, and resume. Fix: require an `enroll`-bound assertion from an existing key (consumed challenge id) for a second key; on `verifyEnrollment` also re-check `keys.length`.
4. **Counter check rejects synced passkeys.** `webauthn.ts:283-286` fails if `newCounter <= key.counter`. Platform and synced passkeys (iCloud, Google) always report counter 0, so 0 <= 0 refuses every approval on phone. The library already implements the correct rule (`counter>0 || stored>0`, `verifyAuthenticationResponse.js:186`); delete the extra check, keep the library's throw, and record clone detection explicitly. Spec acceptance "replayed counter" needs a test.
5. **No tests for the core claims; acceptance fixtures missing.** Spec item 2 requires fixtures: valid, wrong origin, wrong rpId, replayed counter, reused/expired challenge, stale SHA, wrong item, revoked key, cross-item/action reuse, older `holdEpoch`, route-vs-scope matrix; item 1 requires code expiry/single use, second-key rule, revoke, audit. `grep webauthn test/` is empty; `test/unit/console.test.ts` adds one header test. `docs/evidence/slice-12a.md` says "Implemented" for all rows with no test citation. Findings 1-4 would all have been caught.

## Medium

6. **`verify-policy` is a stub; binding is not a fingerprint.** `routes.ts` `passkeyBinding` binds to `policy:<kind>` (the code comment admits it), not a policy fingerprint or change summary; after a successful assertion nothing records a verification, yet the route audits `passkey-approved` and returns `{approved:true}`. `POST /v1/policy/:repo/verify` always returns 403. A human could sign a policy change that differs from what was shown. Either implement against `RepoPolicySource` or return `unavailable` and drop the claim.
7. **Lost-update race in the challenge store.** `verifyAssertion` `:264-291` loads state, awaits the library, then `save(state)` with the stale snapshot; challenges issued (or keys revoked) by concurrent requests during the await are overwritten. `revoke` can be undone by an in-flight assertion (a revoked key reappears). Same for `issueEnrollmentCode` vs `options`. Fix: re-load after the await and mutate only the counter, or serialize with `proper-lockfile` (already a dependency).
8. **Unauthenticated challenge route: no rate limit, store growth, key-ID enumeration.** Spec item 2/5 require rate limiting and audit of invalid attempts. `/v1/approvals/challenge` writes a 2-minute challenge per call with no cap (disk growth, `load` scans every call), and `allowCredentials` (`:226-229`) returns all credential IDs and transports to any caller. `passkeyBinding` failures (`routes.ts`, outside the `try`) are not audited. Add per-peer rate limit and a cap; return allowCredentials only for resident-key (empty list) or after an authenticated session.
9. **Missing notification and audit coverage.** Spec: every enrollment, approval, release and resume is audited and sent to `desktop`/`command`. The PR only calls `audit()`; no notifier call. `revoke` and `issueEnrollmentCode` (`cli/main.ts`, `webauthn.ts:139,152`) are unaudited. `passkey-approved` with `action: enroll` is mislabelled for enrollment (separate event, but credential id is not logged). Add notifier hook and audit entries (no challenge/response bodies, ids only).
10. **Challenge consumed before binding comparison, and bindings are re-derived at assert time.** `take` deletes the challenge on any mismatch (`:241-243`), so an attacker without the challenge id cannot burn it (ids are random), but a stale-head UI retry gets "invalid, expired" with no reason and no audit of the stale SHA. The re-derived binding also trusts the client `item` value: `/assert` accepts `item` from the request, so hold/gate state changes between challenge and assert silently flip to a mismatch error. Acceptable, but return a distinct `stale` error and audit it. Low-risk correctness of the SHA binding itself is good: `approveGate(target.item, sha)` uses the freshly derived SHA.
11. **Confirm UI is thinner than spec 3/3b/4.** `web/app.js` `approvals()` shows only SHA, reasons and verdict: no PR URL, title, diffstat, family, review rule, holder, `holdEpoch`, branch. `confirm()` text is the only prompt. Errors are swallowed (`.catch(() => {})`), so a refused assertion shows nothing. Hold control (3b) is absent. No DOM tests with hostile titles. The daemon, not the daemon-supplied display data, signs only `{item, sha}`; the human cannot verify what was shown.

## Low

12. **Resume challenge has no state check.** `passkeyBinding` for `resume` binds constant `"resume"`; a resume on a non-paused agent still succeeds and writes `resume-request.json` (harmless nudge, but not epoch-bound).
13. **Enrollment code deleted at challenge issue** (`webauthn.ts:201`) rather than on successful registration; a failed or cancelled prompt wastes the code (usability). No attempt throttling on code guesses (entropy 144 bits, so only a DoS concern).
14. **`verifyEnrollment` stores no `userVerified`/`backedUp` info and does not enforce `attestation`/UV beyond `requireUserVerification`**; `userID` is the agent name bytes (stable, guessable). Fine for single-user; note for multi-key credential ID collisions across agents.
15. **`nonce.ts` key is `[action,item,binding]` so `issue` for the same triple overwrites an earlier code** (intended), but `verify` writes the whole file non-atomically against concurrent `issue` (same race as #7). Android path itself is correct: `deliverNonce` is `undefined` for `os: android` (`steward/main.ts`) and the nonce route returns `unavailable` (`routes.ts:355`); but no test.

## Checked and fine

- Bearer/token headers on approval routes are rejected with 403 (`auth.ts:42-52`); the console proxy strips the daemon token on these routes (`proxy.ts`), and the console CSRF/Origin guard (`console/guard.ts`) covers non-GET browser requests. Console cannot approve without a browser assertion.
- Origin and RP ID come from machine-local config, not the request (`webauthn.ts:111,273-274`); UV required both in options and library default (`requireUserVerification` defaults true).
- Challenge is single use (deleted before verification) and expires in 2 minutes; approve binds `{agent, item, gate.sha}`, release binds the current `holdEpoch`; each store is per-agent (`agentDir(agent)`), so no cross-agent mixing.
- Audit entries carry ids and bindings, not assertion payloads.

## Verdict

Not mergeable as "Implemented": fix 1-5 first. Findings 1, 2 and 4 make the feature non-functional on a real phone; finding 3 is an authorization bypass for adding keys.
