# Durable, proactive agents as the base of the portable harness

> **Plan location:** this plan lives in the public repo [`nanstey/durable`](https://github.com/nanstey/durable) at `docs/plan/` (it was drafted under the skills repo's `.plans/` and moved). Paths in the documents are repo-root paths of the **durable repo** unless marked "skills repo". Public-repo rules apply to every file here: no secrets, machine-local state, absolute or personal paths, real host or tailnet names, emails or private repo names.
- Status: slices 1-5 and 6a (dispatcher) shipped; real-profile/operator checkpoints remain pending.
- Summary: Rebuild the harness around Pi Durable: one durable steward process per project scope per machine, one **profile** per agent (credentials stay in machine-local profiles), workers dispatched through a `WorkerDispatcher` adapter (Orca primary), a code-owned review/merge gate that works under the operator's shared GitHub identity, per-repo opt-in auto-merge behind a pluggable `RepoPolicySource` seam (mechanism undecided; auto-merge off by default via the `none` source) proven by shadow mode, a layered control plane (CLI/TUI, local notifications, and a multi-machine web console served from one chosen machine over Tailscale, interactive from any browser, a phone included, with identical capabilities), an additional Android/Termux daemon target behind platform capability flags, and retirement of interactive subagents. Our API, client, TUI and console are written from scratch (the dpi-* projects were inspiration only). The engine lives in the public `nanstey/durable` repo; the skills repo keeps only a thin integration (pinned clone, CLI on PATH, thin skill).
- Tier: large (see Decision log for evidence)

## Decision log

- 2026-10-24 (rev 13, onboarding flow) — Add slices **17a-17d** after 7c, without changing shipped or in-flight work. The first deliverable is `durable onboard`: a three-stage CLI wizard that starts a named machine-local profile, creates or selects a non-secret organization, then creates an agent and runs doctor before enabling it. It is resumable and idempotent: private onboarding state records completed stages and is safe to rerun to add profiles, organizations or agents. `--yes` accepts documented recommended defaults; `--non-interactive --answers <file>` consumes a plain, non-secret answers file so tests and repeat installations are repeatable. Before every write, `--dry-run` shows the complete file diff; credentials are never accepted from, stored in or printed from answers files. GitHub setup binds identity with least-privilege fine-grained-token guidance and an optional device-flow handoff only where the installed `gh` supports it; model setup hands off to Pi `/login`, probes cheaply, and requires explicit Anthropic-OAuth opt-in. Organization setup lists accessible repositories through the selected profile, applies a multi-select `scope.repos`, reuses slice-7b connector allowlists and its fake/Composio custody rules, and supplies safe pipeline/limit/quiet-hour/notification defaults. Agent setup chooses a mission template or custom mission, selects/reuses a code-enforced pipeline, models, dispatcher and workers, then defaults to human approval, shadow mode and auto-merge off. Doctor failures show exact fixes and can be re-checked before enablement; first-run tour follows enablement. Slice 17d adds console onboarding over the same daemon-side API. A sandbox/demo try-first path is optional and never receives credentials; the skills-repo installer links to `durable onboard` but does not run it. Android/Termux uses pure-JS dependencies and the same non-interactive/dry-run path. See specs 17a-17d.
