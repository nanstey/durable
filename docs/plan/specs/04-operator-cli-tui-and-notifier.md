# Spec 04 — Operator CLI/TUI client, chat conversations and notifier core

Objective: the operator can attach to, chat with (follow-up, steer, abort), start and resume conversations with, and inspect any agent on this machine from a terminal, and agents can tell the operator that something needs a decision through local channels. No push service. Merges the first-draft notification slice with the client slice (U1, U2).
Design refs: architecture D1, D10, §3.2 (channels), §3.3; program design §2 (N1, N2), §3.7, §5 (`notify` row).
Revision 3: adds chat conversations (kinds `chat` and `scout`) with the fixed tool set and the enqueue-only `request_merge`/`request_work` tools (architecture D16, program design CH1-CH7); the guardrails themselves shipped in spec 03; desktop notifications are Linux-only (`notify-send`).
Revision 4: the `desktop` channel is platform-aware through a `DesktopNotifier` interface with a `nonceSafe` flag (`notify-send` on Linux is nonce-safe; the Android `termux-notification` backend in spec 14 is not); client library and TUI are written from scratch (U3).
Depends on: spec 03 (API v1, tokens, inbox, chat guardrails). Wire-in of real events happens in specs 05-07; this slice proves delivery with test events.

## Checklist
1. **Typed client** `client/{client,stream,transcript}.ts`: fetch client for API v1 (scopes aware), SSE reader implementing `hello -> snapshot -> deltas` with reconnect and dead-socket detection (45 s), and a transcript model, all written by us from scratch against our own API v1 contract (the dpi-* projects were inspiration only; nothing is copied). Used by the CLI, TUI and later the console hub. Acceptance: tests against a faux daemon (in-process server implementing the v1 contract) including reconnect and slow-viewer drop.
2. **TUI** `tui/*` and `durable attach <agent>`: transcript with tool calls, composer (follow-up by default, steer while busy), abort, side panels for inbox and (when present) queue; local token only. Our own small TUI on our own client library (no `dpi-tui` reuse or compatibility goal). Acceptance: `tmux`-driven smoke test (attach, send, steer, abort, detach); nothing is stopped when the TUI exits.
2b. **Chat conversations** `steward/conversations.ts`, `api/routes.ts`, `cli/chat.ts`: `GET /v1/conversations?kind=&item=`, `POST /v1/conversations {kind: chat|scout, item?, name?}` (kind must be in the definition's `startableKinds`, default `[chat, scout]`; workers and reviewers are never startable; `Idempotency-Key`; no open-conversation cap by default); `durable chat new|list|resume`. A `chat` conversation is a child/fork of the steward `main` conversation; a `scout` conversation is read-only Q&A about one item. **Fixed tool set** (code-defined, same for the steward `main`): `list_queue`, `explain_item`, `status`, `set_priority` (validated; cannot bypass eligibility/trusted-author rules), `pause`, `request_merge` and `request_work` (**enqueue a request only**; the gate/dispatcher evaluate it under policy, budgets, caps, kill switch and eligibility). No resume, approve, merge, definition/policy edit, secret-reading or shell tool exists. System prompt: never ask for or accept credentials. Acceptance: tool-set snapshot test; `request_merge` on a PR the gate would block stays blocked (stub gate); `request_work` for an untrusted-author item stays ineligible; kind/limit tests; chat survives steward restart (durable conversation).
3. **CLI commands**: `durable queue|inbox|audit|ask|status --all`; `durable inbox ack`; `--json` everywhere. Acceptance: tests against the faux daemon.
4. **Event taxonomy** `notify/types.ts`: `approval-needed`, `escalation`, `budget-stop`, `identity-failure`, `agent-down`, `merged`, `digest`; fields: agent, event, target (PR/issue URL), sha, priority, title.
5. **Channels** `notify/channels/*` (only these kinds): `inbox`/`console` (writes `steward.inbox`; Web Push is added by the console in spec 12b), `desktop` (platform-aware `DesktopNotifier`: `notify-send` on Linux, `nonceSafe: true`; missing tool => skip + audit line; the nonce is delivered only to backends with `nonceSafe: true`, PL3), `command` (configured argv, event JSON on stdin, no shell), `github` (review request, @mention or assignment to `targetLogin`; **skipped with an audit note if `targetLogin` equals the agent's profile login**, because GitHub does not notify you about your own activity; behaviour confirmed by the spike). Acceptance: stub binaries and a fake `gh`.
6. **Notifier** `notify/notifier.ts`: maps event -> channels from the definition's `notify` block; **de-dup** key `agent+event+target+sha` with TTL (durable in `steward.notify`); **quiet hours** hold events and deliver later (never drop); **priority**; **reminder cadence** (`afterMinutes`, `everyMinutes`, `max`); **redaction** (ids, titles, URLs only; no bodies, tokens or paths). The CLI approval nonce (spec 07) is the only secret-like payload and only `desktop`/`command` may carry it. Acceptance: dedup, quiet-hours hold + later delivery, reminder caps, redaction grep tests; replay test: crash after send, restart, dedup key prevents a second send.
7. **Stale handling**: after `staleDays` without resolution, park the item as `needs-human`, release claim/workers, post one GitHub comment, send one final `escalation`. Never approve, merge or escalate privileges. Acceptance: fake-clock tests. (Exercised by real items from spec 06.)
8. **`agent-down`**: `durable notify --event agent-down --agent <id>` works with the agent dead (machine file + channels only); `durable-agent-failure@.service` calls it via `OnFailure=`. Acceptance: stub `systemctl`; live drill with restart disabled.
9. **CLI**: `durable notify --test <event> [--agent <id>]`, `durable notify status` (dedup keys, held events, reminder state).
10. **Docs**: `docs/operator.md` (durable repo) gains the control-plane section (layers L0-L3 as revised, channels, quiet hours, what happens when nobody answers, why the nonce only goes to desktop/command, the GitHub self-notification caveat). `docs/` pages in the durable repo. Console is described as planned in slices 8, 11, 12.
11. **Live**: attach to the running steward from the machine and from an Orca terminal; desktop and command-hook notifications; one GitHub notification to a second login if available; `kill -9` with restart disabled produces `agent-down`.

## Risk controls
- Payloads contain ids, titles and URLs only; the inbox and GitHub are agent-readable and never carry secrets.
- Notifier makes outbound calls only (none in this slice besides `gh` and local commands).
- Quiet hours never drop an event.
- The TUI uses the local token with scopes `read`, `chat`, `pause` only.
- Chat conversations cannot widen their own tool set; every message passes the spec 03 guardrails (screening, 1 MiB ceiling, audit; rate limits only if the agent opted in). The `startableKinds` rule is console-wide, not per client type.

## Out of scope
Console, Web Push, ntfy or any third-party push service, inbound action buttons, chat bridges.

## Done when
CI green; live drills recorded; user has attached, received a desktop and a command-hook notification, and judged the TUI's ergonomics.
