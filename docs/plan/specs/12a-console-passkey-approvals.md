# Spec 12a — Passkey-guarded approvals, agent resume, enrollment and policy verification (any browser)

Objective: the operator can perform the **high-risk actions** from the console in **any browser** (a phone passkey is the natural step-up device; a desktop browser can use it through the cross-device flow, checked in the spike) — approve a PR for a merge attempt, resume an agent after a kill/pause, enroll another key, verify a repo policy, release a human hold — using a passkey assertion verified by the **daemon**. Daemon bearer tokens can never do these. Chat, steering, aborting a turn and pausing are not in this class (they ship in specs 08 and 11).
Design refs: architecture D8 (`verify-policy`), D13, D14, D15 (credential classes, residual risks, fallback ladder), D16; program design §2 (A1-A5, C1-C5, N1-N2), §3.6, §3.8, §5 (`approval/webauthn`, `console`, `web` rows).
New in revision 2 (U2, A); revision 3: split out of the old spec 12 so PWA/Web Push (spec 12b) is a separate, non-blocking follow-up; adds a policy action; the phone is already interactive and is not special (spec 11). Revision 5: the action is `verify-policy` (mechanism-independent, display data supplied by the repo's `RepoPolicySource`; it is meaningful once a real source exists and is exercised with the `fixture` source until then); the passkey step-up applies to any browser, not specially to phones.
Revision 4: daemons on Android have no nonce-safe desktop channel (PL3), so this slice is the only in-app approval path for them; a daemon with `os: android` and no enrolled passkey reports approvals as `unavailable: merge in GitHub` and never falls back to a notification nonce.
Revision 7 (review): **release of a human hold** joins the passkey actions: challenge bound to `{agent, action: release, item, holdEpoch}`, console hold/release controls, and cross-item/cross-action reuse tests.
Depends on: spec 11 (HTTPS console reachable over Tailscale), spec 06 (hold fence, `holdEpoch`, release nonce path), spec 07 (approval task, nonce path, reserved approval routes) and, for policy verification, spec 09. Requires the slice 1 go/no-go for passkeys on the phone.

## Checklist
1. **Passkey enrollment** `approval/{keys,challenge}.ts`, `cli/approval.ts`: `durable approval enroll <agent|--all>` on a **TTY** on the daemon's machine prints a short-lived enrollment code (hashed in `steward.approval`); the console page registers a passkey (RP ID = console host FQDN from machine-local `approval.webauthn`; `userVerification: required`; resident key if available); the daemon stores the public key, credential id and counter. The first key requires the enrollment code; additional keys require an existing key's assertion (A3). Every enrollment is audited and sent to `desktop`/`command`. `durable approval list|revoke`. Acceptance: tests for code expiry/single use, second-key rule, revoke, audit entries.
2. **Challenge/assert flow** `approval/{webauthn,challenge}.ts`, daemon routes `POST /v1/approvals/challenge`, `/v1/approvals/assert`, `POST /v1/resume`, `POST /v1/policy/<repo>/verify`, `POST /v1/items/<item>/release` (replacing the `501 not-enrolled` stubs from spec 07; release also keeps its CLI nonce path from spec 06): challenge bound to `{agent, action: approve|resume|enroll|verify-policy|release, item or repo, headSha or policy fingerprint or holdEpoch}`, single use, short expiry, display data generated by the daemon from its own reads (PR URL, title, diffstat, verdict and family, gate reasons; for `verify-policy` the change summary produced by the repo's policy source from the daemon's own reads; A5). Assertion verification (signature, origin and RP ID from machine-local config, counter, enrolled key, challenge unused, **head SHA/fingerprint unchanged**) uses the verifier chosen in the spike (pinned, small, permissive license). On success: `approve` => the steward re-runs the gate at the current head SHA and attempts the merge within GitHub rules (A4); `resume` => the agent leaves the paused state; `enroll` => key added; `verify-policy` => the source records the verification; `release` => the hold fence is cleared only if the item's current `holdEpoch` equals the signed one, then the steward re-derives state (spec 06 item 12b). No bearer scope reaches these routes (A1); invalid attempts are audited and rate-limited. Acceptance: assertion fixtures (valid; wrong origin; wrong rpId; replayed counter; reused/expired challenge; stale SHA/blob; wrong item; revoked key); **cross-item and cross-action reuse**: an assertion over a `release` challenge for item A is rejected on item B, on `approve` and on `resume`, an `approve` assertion is rejected on `release`, and a `release` assertion with an older `holdEpoch` (released, re-held, replayed) is rejected; route-vs-scope matrix test (no bearer scope reaches `release`).
3. **Approvals inbox and confirm UI:** list of `approval-needed` items per agent/machine and policy-change requests; detail shows PR URL (explicit open button), title, diffstat, reviewer verdict and family, gate reasons, **head SHA**, the repo's review rule (a review-required repo says "merge in GitHub"); for policy verification, the source-supplied change summary; a deliberate confirm button starts the passkey prompt; result and audit link shown. All text inert (C3). Acceptance: DOM tests with hostile PR titles and diffs; no auto-submit path; script cannot start an assertion without a user gesture (tested where the harness allows).
3b. **Hold and release controls:** item and worker nodes show **Hold** (a plain `pause`-scope action calling `POST /v1/items/<item>/hold`; the node shows `holding` until the daemon reports `held`) and, on held items, **Release** (detail shows item, branch, current head, who held it and when, `holdEpoch`, foreign-terminal advisory; a deliberate confirm starts the passkey prompt). Before this slice the console shows "release with `durable release` on the machine" instead. Acceptance: DOM tests; agent token cannot release; passkey can; release is audited and sent to `desktop`/`command`.
4. **Agent resume and kill-switch UI:** paused/killed agents show a "resume" action requiring the passkey; pause remains a plain `pause`-scope action. Acceptance: agent token cannot resume; passkey can; resume is audited and sent to `desktop`/`command`.
5. **Console-side defence in depth:** Serve identity header allowlist on all non-GET requests, Host/Origin/CSRF guard, CSP unchanged, rate limiting on challenge routes. Acceptance: tests.
6. **Operator docs:** threat-model section (what the passkey protects against and what it does not: same-OS-user attacker, compromised console misleading the human, stolen unlocked phone, tailnet node compromise); recovery (lost phone: `durable approval revoke`, re-enroll on a TTY); how this differs from chat (chat is rate limited and audited, not passkey-guarded).
7. **Live test from a phone and from a desktop browser:** enroll a passkey (phone), approve one real human-approval-mode PR from each browser, resume a paused agent, verify a changed policy using the `fixture` source (or a real source if one exists); confirm audit entries and the `desktop`/`command` notification of each action; confirm an agent-reachable bearer token gets 403 on the same routes.

## Risk controls
- Approval secrets never exist on any host an agent can read: the private key stays on the operator's device; the daemon stores public keys only.
- Fallback ladder (architecture D15): if passkeys are not viable on the operator's browsers and devices (the same fallback for every browser), skip this slice; interactive chat and pause are unaffected (spec 11); approvals, resume and policy verification use GitHub merge and the CLI nonce on a machine terminal. No TOTP or password fallback.
- The console is a conduit and cannot mint approvals. A compromised console can mislead the human about what is shown; the signed challenge fixes agent, item and SHA/blob, and the human can verify through the GitHub link.
- An approval authorizes only an attempt within GitHub rules (A4); it never changes policy; `verify-policy` only records that a human accepted the change shown.

## Out of scope
PWA install and Web Push (spec 12b); peer-to-peer; hardware-token-only policies; approving from outside the tailnet; editing configuration or policy from the console.

## Done when
CI green; live tests from a phone and a desktop browser recorded; residual risks documented and accepted by the user; or, if the spike's ladder applies, the user explicitly defers this slice.
