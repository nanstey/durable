# Spec 06 — Dispatcher, worker kinds, claims and the Pi-session worker -> draft PR (6a, 6b)

Objective: an eligible item is claimed on GitHub, a **Pi-session worker (the default kind)** implements it in a workspace created through a `WorkerDispatcher` adapter (Orca primary, git-process second) under the profile's identity, and a draft PR appears. Revision 7 separates the dispatcher (where work lives) from the worker kind (what runs there), so the opt-in durable-conversation kind (spec 06c) fits without changing this spec's flow. Caps, kill switch and crash recovery are enforced.
Design refs: architecture D3, D4, D5, D6, D7, D9, §4 steps 3-4, §5; program design §2 (W1-W3, S1, S2, S4), §3.3-3.4.
Revision 1: adds the adapter layer and contract suite (C7); Orca is assumed present on every machine; PR attribution follows the operator-identity design (C2).
Revision 2: renumbered (was 05). Escalation and budget events now use the notifier from spec 04 (no push services); adds `GET /v1/workers` and `workers` SSE frames for the CLI and console.
Revision 3: dispatcher **capabilities** (`attach`, `steer`, `transcript`) and a live worker transcript tail so the console/CLI can view any worker and steer where the adapter allows (architecture D4, D16); worker routes `POST /v1/workers/<id>/steer` (scope `chat`, `501 not_supported` unless `steer: true`) and `/interrupt` (scope `pause`). Orca terminal-input support is checked against the installed CLI (spike result).
Revision 4: `git-process` must work with no Orca installed and is the default dispatcher wherever Orca is not detected (the Android path, spec 14); dispatcher selection consults platform capabilities; `doctor` skips Orca checks when `dispatchers` excludes `orca`.
Revision 7 (U6): the dispatcher contract is split into workspace creation/removal, process hosting and viewers; a `WorkerKind` registry (`pi-session` here, `durable-conversation` in 06c) owns what runs; `openViewer` can open a `durable attach` terminal; `durable open`; the **human-held rule** (`durable hold|release`, advisory foreign-terminal check) lands here; the tree API from spec 03 gains dispatcher-sourced Pi-session leaves. Architecture D4, D19, D20; program design §2 (W1-W3, H1-H3, T1-T3).
Depends on: spec 05 (and spec 04 for notifications, including the TUI tree).
Split (decided): **6a** items 1-4 and 3c (dispatcher, kind registry with `pi-session`, contract suites, capabilities, transcript tail, worker routes, tree leaves; observable by launching a trivial job in Orca and in git-process mode), **6b** items 5-13 including 12b and 12c (claims, brief, Pi-session worker to a draft PR, budgets, hold, viewers).

## Risk controls
- The worker holds the operator's token. Use a fine-grained token limited to the scope's repos, no admin. The guard is a guardrail; branch protection is the real stop. No Workflows write permission.
- Brief and launcher files contain no secrets (env supplies them) and are 0700/0600.
- Only trusted-author items reach the scout.
- Never remove a workspace with uncommitted or unpushed work (adapter contract).
- No `gh pr merge` string in source yet.
- Orca flag drift: the `orca` adapter is the only code that knows the flags; contract tests catch regressions.
- Two writers in one worktree (a human Pi session plus a worker): the human-held rule is the safeguard; the foreign-terminal check is advisory only.

## Out of scope
Reviewer, gate, approval, merge, notifications delivery (event recorded only), second machine, the durable-conversation worker kind (spec 06c), automatic handoff features beyond the minimal hold/release rule.

## Done when
CI green including the contract suite; live pilot produced one draft PR through the `orca` adapter and one through `git-process`; replay and cap tests pass; user reviewed PR, audit trail and machine load.
