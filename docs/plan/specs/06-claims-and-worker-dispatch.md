# Spec 06 — Dispatcher, worker kinds, claims and the Pi-session worker -> draft PR (6a, 6b)

Objective: an eligible item is claimed on GitHub, a **Pi-session worker (the default kind)** implements it in a workspace created through a `WorkerDispatcher` adapter (Orca primary, git-process second) under the profile's identity, and a draft PR appears. Revision 7 separates the dispatcher (where work lives) from the worker kind (what runs there), so the opt-in durable-conversation kind (spec 06c) fits without changing this spec's flow. Caps, kill switch and crash recovery are enforced.
Design refs: architecture D3, D4, D5, D6, D7, D9, §4 steps 3-4, §5; program design §2 (W1-W3, S1, S2, S4), §3.3-3.4.
Revision 1: adds the adapter layer and contract suite (C7); Orca is assumed present on every machine; PR attribution follows the operator-identity design (C2).
Revision 2: renumbered (was 05). Escalation and budget events now use the notifier from spec 04 (no push services); adds `GET /v1/workers` and `workers` SSE frames for the CLI and console.
Revision 3: dispatcher **capabilities** (`attach`, `steer`, `transcript`) and a live worker transcript tail so the console/CLI can view any worker and steer where the adapter allows (architecture D4, D16); worker routes `POST /v1/workers/<id>/steer` (scope `chat`, `501 not_supported` unless `steer: true`) and `/interrupt` (scope `pause`). Orca terminal-input support is checked against the installed CLI (spike result).
Revision 4: `git-process` must work with no Orca installed and is the default dispatcher wherever Orca is not detected (the Android path, spec 14); dispatcher selection consults platform capabilities; `doctor` skips Orca checks when `dispatchers` excludes `orca`.
Revision 7 (U6): the dispatcher contract is split into workspace creation/removal, process hosting and viewers; a `WorkerKind` registry (`pi-session` here, `durable-conversation` in 06c) owns what runs; `openViewer` can open a `durable attach` terminal; `durable open`; the **human-held rule** (`durable hold|release`, advisory foreign-terminal check) lands here; the tree API from spec 03 gains dispatcher-sourced Pi-session leaves. Architecture D4, D19, D20; program design §2 (W1-W3, H1-H3, T1-T3).
Revision 7 (review): hold is a fenced `holding -> held` sequence with item-bound routes; release is approval-class with an action-bound CLI nonce from this slice (passkey in 12a); the launcher passes `--provider` and `--model` separately on initial and continued launches with stdin `/dev/null` for headless runs; kind selection follows program design §2.1; every stop-like operation follows the lifecycle table (program design §2.2); the contract suite names the current dispatcher operations.
Depends on: spec 05 (and spec 04 for notifications, including the TUI tree).
Split (decided): **6a** items 1-4 and 3b (dispatcher, kind registry with `pi-session`, contract suites, capabilities, transcript tail, worker routes, tree leaves; observable by launching a trivial job in Orca and in git-process mode), **6b** items 5-13 including 12b and 12c (claims, brief, Pi-session worker to a draft PR, budgets, hold, viewers).

    12b. **Human-held rule (D19, H1-H5):** `durable hold <agent> <item>` = `POST /v1/items/<item>/hold` (scope `pause`; also a console button on item and worker nodes) runs the **`holding -> held` sequence** `dispatch/hold.ts`: (1) commit the fence `{item, holdEpoch (incremented), state: holding, by, via}` to `steward.holds` before anything else; (2) from that commit on, every daemon operation on the item (dispatch, resume, `kind.start`, code-owned git/GitHub tools, `removeWorkspace`, `beforeTool` for durable workers) checks the fence and is rejected; (3) cancel and drain in-flight work: `kind.interrupt(soft)`, then after `drainSeconds` (default 10) `kind.interrupt(hard)` (durable: explicit abort of `run-worker`, outcome `held`; pi-session: `interruptProcess` hard / Orca `terminal close`); (4) terminate the item's containment (spec 03 item 13b): on Linux kill the attempt slice and **wait until it is recursively empty** (`cgroup.events` `populated 0`), which also catches descendants that left their process group (`setsid`, double fork) or whose leader exited; (5) only when containment is confirmed empty set `state: held`, audit, and acknowledge to the caller. **When containment cannot be confirmed** (Android/Termux, which has no cgroups; or a Linux kill/wait that fails or times out) the item **stays `holding`, never `held`**: daemon operations stay fenced, the tree shows `holding`, and the operator gets an `escalation` and a CLI/console message that says what independent check is needed before editing. **Linux** (kill/wait failure): the message names the slice and `systemctl --user stop durable-<agent>-<item>-<attempt>.slice`, and the operator confirms `populated 0` (`durable hold --verify <item>` reads it). **Android:** stopping the steward alone does **not** establish exclusive ownership (an unmarked `setsid` descendant survives both the steward and the marker sweep), and `/proc` cannot prove that no future writer exists (a descendant with cwd `/` and no open file under the worktree can still write there later by absolute path). So **whenever containment is unconfirmed (Android, or Linux on cgroup v1), exclusive ownership requires force-stopping Termux (Android Settings, Apps, Termux, Force stop, which ends every Termux process) or rebooting the device**; on cgroup v1 Linux it requires a reboot. Without confirmed containment, `durable hold --verify <item>` is **advisory only** (on cgroup v2 Linux it also reports the slice's `populated` state, which is authoritative): it lists processes of the user whose cwd or open files are under the worktree (from `/proc`) to help spot obvious writers, it never establishes ownership, and it never moves the item to `held`. Acknowledgement: the API returns `202 {state: holding}` immediately and the TUI/console wait for the `held` tree status; `durable hold` blocks until `held` or times out with `holding: <reason>`, staying fenced and sending an `escalation`. **Restart:** `steward/main.ts` loads `steward.holds` before `harness.open()` resumes any task, so a `holding` fence finishes its sequence and a `held` fence stays in force before unfinished work can run (H4). The claim and its lease are kept. **Release** is approval-class (H2, A1): `durable release <agent> <item>` asks the daemon to issue an action-bound nonce (`approval/nonce.ts` lands in this slice for `release`; spec 07 adds `approve`/`resume`/`verify-policy` to the same module) delivered only to nonce-safe `desktop`/`command` channels; `durable release <agent> <item> --code <nonce>` (TTY) posts `POST /v1/items/<item>/release {code}`; the daemon checks `sha256(nonce + agent + "release" + item + holdEpoch)`, single use, expiry; no bearer scope reaches the route. After release the steward re-derives state from the branch and starts a new attempt (or review). An advisory `workspaceTerminals` check reports a foreign terminal in a worker's worktree as `suspected human session` in `status` and `doctor`. Acceptance: tests with both adapters and the fake kind: every refused operation listed above while `holding` and `held`; a **delayed writer** (a hosted command that writes into the worktree 10 s after hold) leaves the worktree unchanged after `held`; a worker whose command backgrounds **descendants** (`sleep &`, `nohup`) has none left at `held`; on Linux a **delayed writer that leaves its process group** (`setsid sh -c 'sleep 10; echo x >> f' &`) is killed and `f` is unchanged 15 s after `held`; with a stubbed `systemctl --user kill` that fails, the item stays `holding` and escalates; on a stubbed Android platform hold ends in `holding` with the independent-verification message, every daemon operation still refused, and `durable hold --verify` listing an unmarked `setsid` writer whose cwd is in the worktree (fixture `/proc`) while still printing the force-stop-or-reboot requirement (a fixture writer with cwd `/` is not listed, and the output says so); **restart while holding and while held** (SIGKILL the steward; the fence is enforced before any task resumes; no write, push or resume happens); release impossible with any bearer scope; a release nonce for another item, another action (`approve`/`resume`) or an older `holdEpoch` is rejected; advisory appears.

## Risk controls

- The worker holds the operator's token. Use a fine-grained token limited to the scope's repos, no admin. The guard is a guardrail; branch protection is the real stop. No Workflows write permission.
- Brief and launcher files contain no secrets (env supplies them) and are 0700/0600.
- Only trusted-author items reach the scout.
- Never remove a workspace with uncommitted or unpushed work (adapter contract).
- No `gh pr merge` string in source yet.
- Orca flag drift: the `orca` adapter is the only code that knows the flags; contract tests catch regressions.
- Two writers in one worktree (a human Pi session plus a worker): the fenced hold sequence is the safeguard (held is acknowledged only after in-flight work is drained and process groups are gone); the foreign-terminal check is advisory only.
- Intentional cancellation (abort, interrupt, hold, pause, stop) never silently restarts work (lifecycle table, program design §2.2).

## Out of scope

Reviewer, gate, merge approval (only the `release` nonce lands here), merge, notifications delivery (event recorded only), second machine, the durable-conversation worker kind (spec 06c), automatic handoff features beyond the minimal hold/release rule.

## Done when

CI green including the contract suite; live pilot produced one draft PR through the `orca` adapter and one through `git-process`; replay and cap tests pass; user reviewed PR, audit trail and machine load.
