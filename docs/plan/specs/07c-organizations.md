# Spec 07c — Organizations

Objective: add an optional, cross-machine organization policy boundary that groups durable agents by context. An organization distributes non-secret defaults for pipeline, limits, quiet hours, notifications, repositories, tools and connectors. Profiles remain machine-local credential units: each agent definition names the profile it uses on that machine, and organization policy never stores or selects credentials. An agent without `organization` retains today's behavior through an implicit `default` organization.

Design refs: [organization research](../../research/organizations.md); product review decisions 32-34 and Q29-Q36; architecture D23, D3, D16 and §3; program design §2-3; specs 02, 06b, 07, 07b, 08, 11 and 15.

Depends on: shipped 02-06b and 08, in-flight 06c only for durable-worker coverage, 07 (approval/gate), 07b (connector enforcement), and **11** (cross-machine console links and fleet status). It follows 7b and 11 so Git-backed policy has existing connector enforcement and console-triggered sync. It does not change shipped semantics or reorder slices 8-16.

## Checklist

1. **Organization repository and schema:** add a non-secret, Git-backed organization repository containing `organizations/<name>.yaml`. Each document has `name`, `memberAgents`, shared settings, default pipeline, limits, quiet hours, notifications, allowed tools, allowed connectors with read/write allow/deny classes, and allowed `scope.repos`. `machine.yaml` configures only the read-only remote and cache location. Add optional `organization: <name>` to `AgentDefSchema`; unknown keys, duplicate membership, path-like values and missing named documents fail closed. Acceptance: generated schema/drift and valid/unknown-key/membership fixtures pass.
2. **Versioned publication:** canonical organization version is the Git commit content hash plus an approved release record `{organization, parentHash, contentHash, publisher, approvedAt}`. `durable org publish <name> --code <nonce>` validates the candidate, shows the effective diff, and requires an approval-class nonce bound to name, parent and content hashes before it pushes/marks a release. Bearer tokens, workers and the console cannot publish. Acceptance: nonce replay, wrong-parent/hash, unapproved commit and audit-redaction tests fail closed.
3. **Pull and materialize:** every member daemon pulls at initialization/startup, on a bounded periodic check, and after a slice-11 console sync request. It verifies the approved release and schema, then materializes an immutable effective configuration for that agent, recording organization name, source hash, fetched time and effective-policy hash. The console accelerates pull for reachable machines but is neither source of truth nor required for recovery. Acceptance: startup, periodic, console-triggered and offline-clone fixtures converge to the same materialization.
4. **Default and migration:** an omitted `organization` resolves to the implicit, in-memory `default` organization, which has no remote or sync requirement and permits exactly the existing definition. Do not rewrite existing definitions, machine files or state. Acceptance: fixture snapshots prove pre-organization definition, doctor result, generated environment, dispatch selection and audit semantics are unchanged.
5. **Effective policy and precedence:** compute released organization defaults then agent definition. Agent definitions may narrow repos, tools, connectors, limits, pipeline, quiet hours and notification delivery. They may not add a repo/tool/connector, change read to write, raise a limit, shorten quiet hours, enable a disabled stage or add notification targets. An attempted loosen is a doctor error, never a silent clamp. A released organization update that loosens security-relevant policy is rejected by default and requires a distinct approved publish bound to its exact diff before any member accepts it. Acceptance: precedence and update matrices cover every field.
6. **Local profile resolution and isolation:** materialization never includes a profile, credential alias or credential value. Each agent resolves its own named profile locally after materialization. Environment, source, checkout, dispatch and connector wrappers receive only that profile and the effective organization policy. Acceptance: two machines with different local profile names and contents run the same organization policy; hostile definition, ambient environment and cross-organization access fixtures fail closed for both worker kinds.
7. **Stale, conflict and drift behavior:** Git merge/conflict resolution happens only in the publisher checkout. A daemon never merges into its cache. Failed fetch, conflict, unapproved hash, invalid schema or materialized-file drift preserves the last valid materialization and blocks new source, dispatch and connector work when no valid policy exists. An unreachable member is reported `stale`; it may continue under its last valid same-or-stricter policy until `maxStaleAge`, then stops new work while allowing existing fenced work to finish safely. Acceptance: disconnect, expiry, divergent cache, local edit, bad release and recovery tests pass.
8. **Doctor, audit, metrics and fleet:** add `durable org list|show|sync <name>` and organization-aware doctor rows for membership, version/hash, approved release, materialization drift and stale age per local agent. Slice-11 fleet groups by organization and reports each reachable member's version state: `current|updating|stale|invalid|unreachable`. Audit, work-item, notification, connector and metric records carry organization id and version. Acceptance: text/JSON/API/SSE/console fixtures identify a version mismatch without exposing policy bodies or credentials.
9. **Approvals and stop controls:** global pause remains global. Per-organization pause/resume fences only member agents. Existing agent-level pause/hold, nonce and passkey bindings remain agent/item/SHA-bound. Publication is an approval-class action, distinct from pause or item approval; organization sync cannot release a hold or authorize a merge. Acceptance: pause matrix, restart, nonce/passkey cross-action rejection and global-vs-organization tests pass.
10. **Connector integration:** effective organization connector allow/deny is a mandatory input to spec 07b provider selection and both worker wrappers. A tool must be allowed by agent and released organization policy; writes require both explicit permissions. Acceptance: allow/deny/read/write/version-mismatch matrices pass, while implicit-default behavior remains unchanged.
11. **Documentation and rollout:** document the publisher checkout, approval-class publish, Git remote access, pull timing, console sync, stale behavior, local profile resolution and recovery. Pilot two machines with different profiles and separate repos, including one offline during a tightening update and later convergence. Record answers to Q29-Q36 before live publishing.

## Risk controls

- Git is the only organization policy source of truth. The console only requests pulls and displays status.
- Organization files, release records, caches and audit never contain credentials.
- Every accepted release is content-hash pinned and approval-class published.
- Security-relevant policy is tighten-only by default. A loosening update is rejected until separately approved against its exact diff.
- Offline members retain only a last valid bounded policy and stop new work after `maxStaleAge`.
- The implicit default preserves every shipped path without a remote dependency.

## Out of scope

Organization nesting, multi-user RBAC, organization-owned secrets, a shared database, daemon-to-daemon synchronization, automatic Git conflict resolution, changing GitHub identities, and retroactively changing historical audit records.

## Done when

Schema, publication, pull/materialization, migration/default, precedence, local-profile isolation, stale/conflict/drift, doctor, fleet, approval/pause, connector, audit/metrics and two-worker-kind tests pass. A two-machine pilot confirms a tightening update converges, an offline member stops after the stale bound, and no organization path exposes or selects credentials.
