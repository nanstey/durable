# Spec 11 — Console across machines over Tailscale (any browser, phone included; interactive)

Objective: the console running on one chosen machine shows and controls the steward daemons of several machines over the tailnet, while every daemon stays independent. The console is a viewer/controller, not a coordinator. The same slice makes the console usable from a **phone** over Tailscale Serve HTTPS **with interactive chat**; passkey-guarded approvals are spec 12a and PWA/Web Push is spec 12b (follow-up).
Design refs: architecture §1 (multi-machine view), D13, D14; program design §2 (D1-D4, C1-C5), §3.6, §5 (`api`, `console/*` rows).
New in revision 2 (U2, C). Revision 3: Q5 answered (tags created at this slice); phone path is interactive (Q17), scope `steer` renamed `chat`, chat guardrails verified end to end through the proxy.
Revision 5: no phone-specific capabilities or gating; any browser client behaves the same. Revision 4: the daemon's peer check is **capability-detected** (`network.peerCheck: required | optional | off`): `required` needs the Tailscale CLI (`tailscaleCli: true`); with `false` (Android) the check is reported `unavailable (optional)` and the bearer token plus the tailnet's own ACL remain the baseline; `network.tailnetAddress` lets the operator set the bind address explicitly where interface enumeration fails; the console shows platform capabilities per device. Console and client library are written from scratch (U3).
Depends on: spec 08. Spec 10 (second physical machine) is helpful but **not required**: the test rig below covers two daemons on one machine.

## Checklist
1. **Tailnet listener** `api/net.ts`: `network.bind: tailnet` (machine file) adds a listener on the machine's Tailscale interface address (never `0.0.0.0`, never LAN); loopback keeps serving the local CLI; retries the tailnet bind until Tailscale is up. Peer check: ask the local Tailscale API (`whois`) for each connection's peer node/tags/user and require a match in `network.allowedPeers` (for example `tag:durable-console`) **in addition to** a valid bearer token. Result of the slice 1 spike (Tailscale facts) chooses the exact local API call. With `peerCheck: required` and no `whois`, refuse the tailnet bind (fail closed). With `peerCheck: optional` (declared, `tailscaleCli: false`), bind anyway, audit `peer-check: unavailable`, and show it in `doctor` and the console; approval-class actions never rely on the peer check (PL4). Acceptance: stub local Tailscale API tests (allowed peer, denied peer, unknown peer, API down => refuse); bind-address test; doctor checks the setting (Tailscale up, tags present) and warns on missing allowlist.
2. **Port assignment:** per-agent daemon ports from `machine.yaml` (`daemon.portBase` + stable allocation recorded in `agents/<id>/port`, or explicit), collision check in doctor. Acceptance: tests.
3. **Token lifecycle for remote clients:** `durable token create --client console-<host> --scopes read,chat,pause`; rotation procedure documented and tested (create new, switch the console registry, revoke old); default expiry 90 days with a doctor warning at 14 days; tokens never in profile secrets (reason documented: `profile-secrets` exports them to agent environments). Acceptance: rotation test with no downtime for an open SSE stream (reconnects with the new token).
4. **Console registry** `console/registry.ts` for remote devices: `durable console add-device --machine <label> --agent <id> --url <https|http tailnet url>` reads the token from stdin (never argv), records the daemon `uid` after first contact, writes `devices.yaml` and per-device token files (0600). `durable console devices` lists status. Acceptance: tests; file modes; token not printed.
5. **Multi-device monitor and mux (with the conversation tree):** status machine per device across many daemons; mux keys `<device>/agent/<aid>` and `<device>/steward`; `mismatch` when `uid` changes; `incompatible` when `apiVersion` is out of range; per-machine grouping in the tree (machine -> agent -> the conversation tree of steward, chat, scout, workers and durable children, with the capabilities each daemon reports); fleet totals. Acceptance: test with N stub daemons incl. flapping and slow daemons (slow one must not block the others).
6. **Independence proof:** automated test where the console process is killed mid-stream and the agents (faux model) keep ticking, claiming (fake GitHub) and gating; restarting the console restores the view with no agent-side change. Document the stance in the README: console is optional, can run on more than one machine, holds no coordination state.
7. **Browser-facing HTTPS (no phone work yet):** `durable console serve` prints, or runs with confirmation, the documented `tailscale serve --bg https` command for the console's loopback listener (never `funnel`; the command refuses any `funnel` flag). Browser requests carry the Serve identity header; non-GET requests require `Tailscale-User-Login` in `console.allowedUsers` plus the guard and CSRF header from spec 08. Acceptance: tests with forged and missing headers; Host/Origin tests behind the proxy hostname.
8. **ACL tags and guidance (Q5: yes, created now):** the operator creates `tag:durable-daemon` and `tag:durable-console` in the tailnet policy and applies the rule set; `durable doctor --acl` prints the exact snippet and checks node tags via the local Tailscale API, never editing the policy. Docs (`docs/network.md` and `docs/operator.md`): `tag:durable-daemon`, `tag:durable-console`; allow console -> daemon port range; allow the operator's devices -> console:443; no daemon-to-daemon rule; phones do not reach daemon ports. Doctor can print the suggested ACL snippet but never edits it.
9. **Test rig** (`tests/rig/`): two daemons on one machine with separate `DURABLE_HOME`s, ports and profiles; a second loopback address standing in for a tailnet peer; stub `whois`. Used by CI where possible and by the live checks.
10. **Any-browser path (interactive; the phone is just another browser client, Q19):** from a laptop browser and from a phone on the tailnet over the Serve HTTPS URL (identity allowlist applied), with **identical capabilities and guardrails**: fleet view, live transcripts, follow-up and steer, abort a turn, start a **chat** or **scout** conversation and resume existing ones, pause an agent, interrupt a worker; steer a worker only where the adapter reports `steer: true`. Chat guardrails (credential screening, size ceiling, audit with the Serve identity login; opt-in rate limit) are verified end to end through the proxy. No client has approve/agent-resume/enroll/policy-verification controls yet. Acceptance: proxy-level tests (screening error display, 429 propagation only when the opt-in is set, no token in any browser-visible payload); a checklist run on a laptop browser and on a phone with the same results; responsive layout checked at phone width over HTTPS; the install-to-home-screen/push pieces are explicitly not part of this slice.
11. **Live:** console host + at least one other machine over the real tailnet (two local daemons if spec 10 has not shipped): tree shows both; chat with one from a phone and from a laptop, pause another; rotate a token; unplug the console host and confirm the agents continue (check GitHub-side activity).

## Risk controls
- The console host holds a scoped token for every daemon (concentration risk, R22): tokens carry no approve/agent-resume/enroll/policy-verification power, expire, and are revocable per client on each daemon. With the `chat` scope a stolen phone session can talk to agents within the guardrail limits (R35); it cannot approve or reach credentials.
- Tailnet membership alone is not trust: ACL tags + daemon `whois` allowlist + bearer token. Serve identity headers never authorize approvals.
- Never Funnel or public exposure; never `0.0.0.0`.
- Daemons do not initiate connections to the console or to each other.
- Same-host agents can reach the console's loopback backend and forge identity headers: headers only gate operations an agent token already allows (D14).

## Out of scope
PWA/home-screen install and Web Push (spec 12b), passkeys and approvals (spec 12a); peer-to-peer messaging; multiple consoles coordinating with each other.

## Done when
CI green including the two-daemon rig; live multi-machine check recorded; independence test passes; user has chatted with an agent from a laptop browser and from a phone over the tailnet and reviewed token handling and the ACL tags.
