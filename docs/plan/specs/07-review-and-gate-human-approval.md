# Spec 07 — Cross-family review, gate (human approval) and approval task

Objective: every worker PR gets an independent review from the opposite model family, a code-owned gate decision, and a durable human-approval wait that works under the operator's shared GitHub identity. Nothing merges in this slice.
Design refs: architecture D6, D8, D9, §4 steps 5-6; program design §2 (G1-G4, G6-G8, nonce), §3.3 (review, gate).
Revision 1: redesigned for the operator-identity consequence (C2): no GitHub self-approval, forgeable GitHub signals, out-of-band approval nonce, human merge as the strongest approval.
Revision 2: nonce delivered only to `desktop` and `command` channels (the console inbox and GitHub are agent-readable); the console inbox gets a nonce-free `approval-needed` request; the daemon's approval routes are credential-class based (architecture D15, program design A1-A4) so the passkey path in spec 12a plugs in without API changes.
Revision 5 (Q18): no policy file or trust-pin design is assumed anywhere; the hard-path rule is mechanism-independent. Revision 3: the **hard-path rule** (PRs touching CODEOWNERS variants or `.github/**` are always `wait-human` and never auto-path; spec 09 adds any policy source's protected locations) and the tighten-only effective policy from the definition land here; the `RepoPolicySource` seam and `verify-policy` land in spec 09. The approval credential class already lists the actions `approve`, `resume`, `enroll`, `verify-policy` (CLI nonce path); resume of a paused agent is `durable resume` with the nonce from this slice onward.
Revision 7 (review): the reviewer result is kind-neutral (`ReviewResult` + `ModelProvenance`, program design §2) so a read-only durable reviewer (spec 06c item 11, code-owned `report_verdict`) and a Pi-session reviewer (verdict file + session log) feed the same record; the action-bound nonce module from spec 06 (`release`) gains `approve`, `resume` and `verify-policy`, and the hash binds the action.
Revision 8 (Warp research): when a project's pipeline selects the optional `spec` stage, `pipeline/spec.ts` creates a draft-PR spec from the read-only scout result and code waits for human approval before dispatch.
Depends on: spec 06 (PRs exist; `approval/nonce.ts` with `release`) and spec 04 (notifier delivers `approval-needed`).

## Checklist

0. **Optional spec gate:** `pipeline/spec.ts` evaluates the code-owned eligibility size (source-declared/judge `size`, optional and demote-only) against `complexityThreshold`. It opens the draft spec PR itself from the read-only scout text, using an intent-first idempotent name keyed by work-item id so restart reuses it; the scout never writes. If size is missing or the judge is disabled, spec is skipped when `specApproval` is false and the item parks `needs-human` when true. Above threshold, the work item enters `waiting-spec-approval`; only an explicit `approval/nonce.ts` `approve-spec` action bound to work-item id, spec PR number and head SHA may move it to dispatch. A new spec commit voids it; no bearer scope can approve, and labels/comments never count. A missing, denied, stale or changed spec stays waiting or parks the item; a worker cannot start it. The default pipeline has no spec stage. Acceptance: threshold boundary, restart/idempotent-PR, missing-size, forged-comment and worker-start-before-approval tests; nonce cross-item/PR/SHA refusal and new-commit invalidation; human approval then permits exactly one dispatch.

1. **Policy + facts** `gate/{policy,hardPaths,tighten,facts}.ts`: `EffectivePolicy` built from the definition's `merge` ceiling and `tighten` block (can only restrict, clamped with a warning; in this slice there is no policy source yet, so auto stays disabled); `isHardPath` (`CODEOWNERS`, `.github/CODEOWNERS`, `docs/CODEOWNERS`, `.github/**`; the source-declared protected locations are added in spec 09); `collectFacts(pr, headSha)` using `gh pr view --json isDraft,author,headRefOid,mergeStateStatus,reviewDecision,statusCheckRollup,files,additions,deletions,reviews`. Unknown/failed reads yield `null`. Only GitHub-computed fields and steward records are inputs (G6). `reviews` from the PR author's own login are ignored. Acceptance: fixture tests over recorded, scrubbed `gh` outputs (add a small recording helper script under `tests/`, never run in CI).
2. **Decide** `gate/decide.ts`: pure, per D8 and G1-G4, G6-G8. Modes `never` and `human-approval` return `wait-human`; `REVIEW_REQUIRED` returns `wait-human` with reason `github-requires-approval-from-other-account`; the `merge` branch exists but the executor only runs it in spec 09. Hard-path PRs return `wait-human` with reason `policy-or-owner-file-change` (G12) in every mode. The approval class also exposes `resume` (un-pause after a kill) via `durable resume` + nonce, and reserves `verify-policy` for spec 09. Acceptance: truth table; **property test** (flipping any required fact to false/null never yields `merge`; LLM-derived inputs only lower the result); **G6 test** (forged labels, comments, statuses authored by the operator identity have no effect, except `durable/hold` which can only block).
3. **Reviewer job** `gate/review.ts` + `templates/reviewer-brief.md`: launch a reviewer through the dispatcher and a worker kind (role `reviewer`, read-only checkout of the PR head; kind `pi-session` by default, or `durable-conversation` when spec 06c exists and the agent allows it for reviewers; a durable reviewer needs an opposite-family model resolvable through the profile, DW9) with the opposite model family (family rules copied from `harness/pi/bin/pi-improve` with a drift test); the result is a kind-neutral **`ReviewResult`** `{verdict: approve|changes|blocked, risk: low|medium|high, summary, headSha}` plus **`ModelProvenance`** `{provider, model, family, entries, source}`: a **Pi-session** reviewer writes `ReviewResult` as JSON to a steward-provided file outside the checkout (schema-validated) and provenance comes from its session log's successful assistant messages (`source: pi-session-log`); a **durable** reviewer calls the code-owned `report_verdict` tool (spec 06c item 11) and provenance comes from the child conversation's assistant entries (`source: durable-entries`). Either way the steward records `steward.reviews` with `sha`, the result and the provenance; the family check runs on **every** successful assistant entry (a fallback can change family); any same-family entry => verdict refused and the review re-run; a `headSha` that differs from the reviewed SHA => rejected. Acceptance (run for **both kinds**): same-family config refused by doctor and launch; valid result recorded with provenance; malformed result rejected; missing result => reviewer failed (no verdict); a same-family fallback entry refuses the verdict; new commit voids the verdict.
4. **Mirror for humans** (display only): commit status `durable/review` on the head SHA (skipped with an audit note if the token lacks the permission) and one PR comment per head SHA with marker `<!-- durable-gate sha=<sha> -->` containing the gate report (facts table, reasons, verdict, action). Acceptance: idempotent; the gate never reads these back.
5. **Approval task** `gate/approval.ts`: durable task through restarts. `issueNonce(item, sha)` -> delivered **only** to the `desktop` and `command` channels of `notify(approval-needed)` whose backend reports `nonceSafe: true` (Linux `notify-send`, the operator's `command` hook; **never** the Android `termux-notification` backend, PL3) (never the console inbox, GitHub or any API-readable place); the inbox/console and GitHub get a nonce-free request with the PR URL; steward stores `sha256(nonce + agent + action + item + sha)` + expiry (the same action-bound hash as `release` in spec 06, where `holdEpoch` takes the place of `sha`); single use; invalidated by a new head SHA; never logged, never written to a file, comment, label or status. Resolution paths: (a) PR **merged by someone else** (steward observes `MERGED`, records "merged by human"); (b) an approving review from an account other than the profile login appears -> gate re-runs at the current SHA; (c) `durable approve <agent> <pr> --code <nonce>` (requires a TTY unless the operator's own shell sets `DURABLE_NONINTERACTIVE_OK=1`) -> authorizes the steward to attempt the merge **within GitHub rules** (mode must allow; otherwise it reports why and stops). Changes requested or rejection requeues to the worker with the review text as input (trusted source only). Acceptance: restart during the wait (no duplicate comment/notification, wait continues); nonce tests (reuse, expiry, SHA change, wrong code, constant-time compare, an `approve` nonce rejected for another item or for `release`/`resume`, and a `release` nonce rejected for `approve`); grep test that the nonce appears in no log, file, inbox entry, API response or GitHub payload. Also implement the daemon's approval routes as credential classes: `POST /v1/approvals/nonce` works; `challenge`/`assert` exist but answer `501 not-enrolled` until spec 12a; assert that **no bearer scope** reaches any approval route (A1).
6. **Ready-for-review transition**: `gh pr ready`, `approval-needed` notification with the PR URL (reminders per cadence), request reviews from `merge.approvers` if configured. Mode `never` stops at ready-for-review with no approval task.
7. **CLI/API**: `durable approve`, `GET /v1/gate/<item>`, `GET /v1/queue` shows gate state; audit lines for review, decision, approval path used, rejection.
8. **Repos that require approving reviews** (shared-identity case): gate reports `wait-human` with the reason; operator guidance printed by `durable approve` ("merge in GitHub, or approve from another account"); no bypass exists. Acceptance: recorded `REVIEW_REQUIRED` fixture test; live check on one such repo if available.
9. **Live**: full path on a real PR from slice 6 or a new one; resolve once by human merge, once by `durable approve --code` on a repo with no required reviews.
10. **Docs**: `docs/operator.md` (approval flow, the nonce, why GitHub labels/comments are not approvals under a shared identity, threat model limits).

## Risk controls

- The reviewer and producer families differ; verify from the launch spec **and** the recorded `ModelProvenance` (session log or durable entries); refuse otherwise.
- The nonce is the only approval secret and is out-of-band (desktop/command only); a worker session never sees it, and the agent-readable inbox and GitHub never carry it. Because workers share the operator's OS user and token, this defends against accidents and prompt injection, not a fully compromised worker (documented).
- The gate does not read forgeable GitHub signals (G6). `durable/hold` can only block.
- Never act on comment text from non-trusted authors.
- No merge call exists in this slice's executor path.

## Out of scope

Merging by the steward; enabling `auto-when-safe`; the web console.

## Done when

CI green; live PR shows the gate report and waits; at least two resolution paths proven; user accepts report format, notification flow and the shared-identity approval behaviour (Q10).
