# Spec 06c — Durable-conversation worker kind (opt-in, alongside Pi-session)

Objective: add a second worker kind in which the steward asks the dispatcher to create the Orca (or git) workspace/worktree and then runs a **headless pi-durable child conversation** whose cwd and file/shell tools are confined to that worktree. It opens a draft PR through code-owned tools, is visible in the tree and in an Orca `durable attach` viewer terminal, resumes natively after a crash, and is stopped by the kill switch. The Pi-session kind (spec 06) stays the **default**; this kind is opt-in per agent or role.
Design refs: architecture D4 (kinds and capability table), D19 (ownership, tools, kill switch, recovery, skills, storage constraint, human-held rule), D20 (tree and viewer), D9; program design §2 (DW1-DW9, H1-H3, T1-T3, W3), §3.3, §3.4, §5.
New in revision 7 (U6, option 1). Pi-durable references: its README "Abort and Subagents" and examples 22, 23, 24, 26, 28, 29 (github.com/earendil-works/pi). The API is experimental (1.4.0); the slice 1 addendum results must be in `docs/evidence/spike-durable-workers.md` before this spec starts.
Revision 7 (review): `bash` runs with the minimal `durable-shell` environment (no `GH_TOKEN`/`GITHUB_TOKEN`, no profile secrets); confinement is stated as **advisory guardrails, not a boundary** (outside-worktree access is possible; known-limit tests; sandbox hardening deferred to a follow-up spec); push/PR tools persist operation intent and reconcile ambiguous outcomes; durable reviewers report a structured verdict with model provenance; lifecycle operations follow program design §2.2; a measurable responsiveness threshold.
Depends on: spec 06 (dispatcher, kind registry, contract suites, hold, viewers), spec 03 (tree API, process containment), spec 04 (tree TUI) and the slice 1 addendum with the go results listed in spec 01 "Addendum done when".

## Checklist

1. **Kind skeleton** `workers/durableConversation.ts` implementing `WorkerKind` (program design §2): capabilities `{attach: interactive via durable attach, steer: true, transcript: native, interrupt: true, resumeAfterCrash: true, skills: allowlisted-text, extensions: false, anthropicOAuth: modelAuth-option, headless: true, processIsolated: false, tokenInShell: false, viewable: durable-attach}`; selection `workers/select.ts` per the precedence and truth table in program design §2.1 (machine per-role override > definition per-role `roles.<role>.kind` > definition `workers.kind` > platform default; enablement by `workers.durable.enabledRoles` is checked after selection and never selects by itself). Acceptance (selection): one test per truth-table row. Acceptance: the spec 06 **kind contract suite** passes for this kind with a faux model, including capability reporting and 501 on unsupported operations.
2. **Ownership and anchor** `workers/durable/anchor.ts` (DW1): `run-worker` is a **background** task owned by the item's `WorkItemTask`; the child conversation is created in one transaction with `ownership: { kind: "task", taskId }` and the agent configuration (model, cwd = worktree, fixed tool set, no `subagent`); a rerun reuses it through `scanConversations({ ownerTaskId })`; `details({ conversationId })` lets UIs attach. Acceptance: aborting the steward main conversation or a chat turn leaves the worker running; a restart re-attaches without a second child.
3. **Tool set and guardrails** `workers/durable/{tools,confine}.ts` (DW3, DW4): `read`, `edit`, `write` with realpath containment inside the worktree and outside `.git/` (enforced, for these file tools only); `bash` with cwd = worktree, each call in the attempt's containment unit (spec 03 item 13b) and the **`durable-shell`** environment from `buildAgentEnv(def, machine, "durable-shell")` (spec 02 item 6: no `GH_TOKEN`, no `GITHUB_TOKEN`, no profile secrets, no provider keys, scratch `HOME`/`TMPDIR`, credential-free gitconfig); the shared `guard/commands.ts` block-list in `beforeTool` (push, merge, rebase, `reset --hard`, branch switching, `git worktree`, `gh pr merge`, `--admin`, `--force`, `cd`/absolute paths outside the worktree); tool outputs screened for credentials. **Contract: these are advisory guardrails against mistakes, not a security boundary** (R47). The model runs `bash` as the operator's OS user, so reading or writing outside the worktree remains possible (an interpreter `python -c`/`node -e`, a script written into the worktree and then run, variable-built paths, reading credential files such as `auth-profiles/*.json`, `secrets/*.env`, `~/.config/gh/hosts.yml`, `~/.git-credentials` by absolute path). The only guarantee is that **credentials are omitted from the shell environment** (neither token alias nor any profile secret). The code-owned tools are the **supported, guarded** write path to GitHub (fixed refspec, replay-safe intent, hooks neutralized), not an enforced one: because the shell can read credential files the OS user can read, a model could push or call the GitHub API directly; GitHub rules, the fine-grained token's scope, budgets, the kill switch and the gate remain the stops. Sandbox hardening (bubblewrap or a per-conversation container) is **deferred** with its configuration to a follow-up spec, written only if the slice 1 addendum item 6 justifies it. Acceptance: file-tool escapes (`..`, absolute paths, symlinks) refused; guard cases (`cd /`, blocked git commands) refused; a hostile-env + profile-secrets test proves neither token alias nor any profile secret is in the shell (`env` output); snapshot of the exposed tool set; a **known-limits suite** (`test/contract/durable-known-limits.test.ts`) that runs the interpreter, script and credential-file-read cases and asserts the documented result: they are **not prevented** (including a direct `git push` with a token read from a credential file against a local bare remote), so the test fails if the docs ever claim otherwise.
4. **Code-owned git/GitHub tools** (DW5) `workers/durable/gitops.ts`: `commit` (manifest identity, `Durable-Agent` trailer), `push_branch`, `open_draft_pr`, `report`. **Operation intent first:** before any network effect the tool commits `steward.ops/<attemptId>` = `{attemptId, op, repo (definition slug), branch durable/<id>/<item>, commitSha (the exact local commit, resolved once), expectedRemoteHead (sha or absent), state: intent}`; one op per (item, op) is in flight at a time (a concurrent call gets `busy` and the same record). **Push the exact commit:** `git push https://github.com/<repo>.git <commitSha>:refs/heads/<branch>` as a plain fast-forward push (never `+`, `--force` or `--force-with-lease`), preceded and followed by a remote-head read through the GitHub API (`gh api repos/<repo>/git/ref/heads/<branch>`); a remote head other than `expectedRemoteHead` before the push stops with `conflict` (no push). **Reconcile ambiguous outcomes** (crash, timeout or lost response; and every `interrupted` replay): read the remote head: `== commitSha` -> `confirmed`; `== expectedRemoteHead` -> not applied, retry the same record; anything else -> `conflict`: stop, mark the item `needs-human`, never overwrite. `open_draft_pr` records `{attemptId, repo, head branch, base, commitSha}`, looks up open PRs for the head branch (and the marker carrying the item) before creating, after an ambiguous create re-looks-up instead of re-creating, and refuses if the PR's head SHA differs from `commitSha`. **No worktree-controlled git behaviour:** every code-owned git call runs with `-c core.hooksPath=/dev/null -c core.fsmonitor=false`, `GIT_CONFIG_SYSTEM=/dev/null` and a steward-generated `GIT_CONFIG_GLOBAL`; the push runs from a steward-owned git dir (`$DURABLE_HOME/agents/<id>/git/<repo>.git`, objects fetched from the worktree by sha) whose config the steward rewrites and hash-checks before each push, with an explicit URL and the token supplied only to that one invocation through a credential-helper argument, so repo-local `remote.*.pushurl`, `url.*.insteadOf`, `credential.helper`, `core.sshCommand` and hooks in the worktree have no effect. Acceptance (fake GitHub + local bare remote): **response lost after a successful push** (the stub drops the reply; reconcile finds `commitSha`, no second push); **intervening branch change** (remote head moved by someone else before or during the retry -> `conflict`, nothing overwritten); **concurrent retries** (two calls for the same item -> one push, one `busy`); **hostile worktree git config and hooks** (`pushurl` to another repo, `insteadOf`, `credential.helper` script, `core.hooksPath`, `core.fsmonitor`, `pre-push`/`pre-commit`/`reference-transaction` hooks writing a marker file and dumping env) -> no hook or helper runs, the token reaches none of them, the push lands only on `<repo>:<branch>`; PR create with a lost response -> one PR; rerun after interruption -> no duplicate push or PR.
5. **Kill switch, limits and holds** `workers/durable/limits.ts` (DW2), with exactly the effects in the lifecycle table (program design §2.2): a `beforeTool` hook checks the kill switch, the hold fence and the item's budgets (`itemMinutes`, `maxTurns`, `maxToolCalls`, token budget from the conversation usage document); the `WorkItemTask` watches the same signals and **explicitly aborts `run-worker`** (crossing the background boundary, writing a terminal outcome `paused|held|stopped|limit|interrupted`) and terminates the item's containment unit (spec 03 item 13b); `durable stop --workers` and `pause` use `abort({ background: true })` plus the outcome; the tree `abort` on a worker node aborts only the current turn (the worker waits for a follow-up); the hold sequence is spec 06 item 12b; daemon `close()` writes no outcome. Acceptance: the lifecycle tests (program design §5 `lifecycle` row) for this kind: each of abort turn, interrupt soft/hard, hold, pause/kill switch, stop workers, budget and wall-clock stops or suspends a running worker as the table says and **no new turn or attempt starts without the listed restart action, including across a steward restart**; `close()` and `kill -9` leave it resumable.
6. **Crash recovery** (DW6): non-replay-safe tools return `interrupted`; steward-authored playbook (`workers/durable/playbook.ts`) tells the model to inspect `git status` and files before repeating; `WorkItemTask` re-attaches after restart. Acceptance: `SIGKILL` mid-`bash`, restart, one worker, one PR; the `bash` call's containment unit (including a backgrounded and a `setsid` child on Linux) is gone before the child conversation resumes (the attempt slice's cgroup on Linux, the group + marker sweep on Android).
7. **Skills** `workers/durable/skills.ts` (DW7): **no user skills, extensions, prompts or packages**; `workers.durable.skills` allowlist (default empty) reads `SKILL.md` body text only from the Pi directory's `skills/<name>/`, size-capped, inlined as a prompt section; an entry whose text requires `subagent`, `codemode` or helper scripts is rejected with a clear reason. Document which workflows stay on Pi-session workers (`idea-to-pr`, `build`, `review-code`, `planning`, anything orchestrating subagents or running skill scripts) in `docs/workers.md`. Acceptance: allowlist tests; one real small skill followed by the faux/real model.
8. **Concurrency and storage constraint** (DW8): `maxConcurrent` (default 2; Android 1) enforced in code; the single-owner storage means all durable workers live in the steward process; configurable retention/export/prune of finished worker conversations if the spike showed it is possible. Acceptance: the (cap+1)th start is queued or refused; **responsiveness threshold** (load test, faux model, each child running a busy loop of `bash` calls and streamed turns, 5 minutes): with `maxConcurrent` children (2) and with 4, the steward API p95 latency for `GET /v1/device` and `GET /v1/conversations?tree=true` stays **below 250 ms**, p99 below 1 s, and SSE heartbeat **lateness** (actual minus scheduled send time of each `: ping`, which is due every 15 s) stays **below 2 s** (thresholds configurable; the slice 1 addendum's baseline is recorded next to the result); a failing threshold blocks raising `maxConcurrent` and is reported at the checkpoint.
9. **Models** (DW9): children use `createModelsFor(profile, providers)`; Anthropic OAuth only when the `modelAuth` option is on; a durable reviewer needs an opposite-family model resolvable before launch or launch is refused. Acceptance: doctor and launch tests.
10. **Tree and viewer:** the worker appears as `worker-durable`/`reviewer-durable` under the steward in `GET /v1/conversations?tree=true`; `durable attach` shows it with follow-up, steer and abort; with `workers.durable.viewer: on-start` the `orca` adapter calls `openViewer` (fallback: command string). Acceptance: tree tests; stub-Orca test for the viewer; live check.
11. **Roles:** reviewer (read-only: `read`, search, a code-owned `pr_diff`, and the code-owned **`report_verdict`** tool; no `bash`, no write tools) is the first role enabled (example in architecture §3.1: reviewer only); code-writing workers are opt-in per agent. `report_verdict` takes the kind-neutral `ReviewResult` (program design §2: `{verdict: approve|changes|blocked, risk, summary, headSha}`), validates it against the schema and the reviewed head SHA, and accepts one final call per attempt; the steward records it with `ModelProvenance` taken from the child conversation's assistant entries (provider and model recorded on each successful assistant entry). Spec 07's reviewer job may use either kind through the same `ReviewResult` + `ModelProvenance` contract. Acceptance: reviewer flow on the durable kind with a faux model: valid verdict recorded with provenance; malformed or wrong-SHA verdict rejected; no verdict -> reviewer failed; a same-family assistant entry (fallback) -> verdict refused and rerun.
12. **Docs and live pilot:** `docs/workers.md` (kinds, capability table, limits, what stays on Pi sessions, the lifecycle table, the guardrails-not-a-boundary statement with the known-limits list; sandbox hardening is a deferred follow-up). Live pilot: one low-risk issue with each kind on the same repo; kill the steward mid-run; hold and release; compare results.

## Risk controls

- Pi-session stays the default; no silent fallback between kinds.
- Confinement is **advisory**: file-tool realpath checks plus cwd and a command denylist for `bash`, **not a sandbox**; outside-worktree reads and writes through `bash` are possible and documented (known-limits suite, R47); neither token alias nor any profile secret is in the shell environment (the only guarantee); code-owned tools are the supported write path, not an enforced one; sandbox hardening is deferred to a follow-up spec.
- Worker progress survives a chat abort or loop tick; the kill switch, hold and limits still stop it with a terminal outcome.
- Experimental pi-durable subagent API: isolated behind `steward/harness.ts` and the kind contract suite; upgrades follow the pin policy.
- Shared process and event loop: `maxConcurrent`, load test, and one steward crash interrupts all in-flight worker tools (documented).
- Two writers in one worktree: the human-held rule applies to this kind too.

## Out of scope

User skills runtime, Pi extensions in durable workers, nested subagents, running durable workers in another process or machine, container/sandbox hardening unless the spike justified a follow-up spec, automatic handoff features.

## Done when

CI green incl. the DW1-DW9 tests and both kind contract suites; live pilot compared both kinds; the user decides which roles use the durable kind (Pi-session remains the default).
