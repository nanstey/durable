## Slice 12a — Passkey-guarded approvals, agent resume, enrollment and policy verification (any browser)

- **Observable outcome:** the operator enrolls a passkey (first key by TTY code), sees the approvals inbox in any browser (a phone passkey is the natural step-up device; desktop browsers may use it via the cross-device flow, to be checked in the spike), and with a passkey assertion verified by the daemon can **approve** a human-approval PR (merge attempt within GitHub rules), **resume an agent after a kill/pause**, **release a human hold** (challenge bound to item and `holdEpoch`; console Hold/Release controls), **enroll** another key, and **verify a repo policy** (the `verify-policy` action; display data supplied by the policy source; meaningful once a real source exists, exercised with the `fixture` source until then). A bearer token cannot do any of these. A stale head SHA or blob fails.
- **Layers:** `approval/{webauthn,keys,challenge}`, daemon approval routes (replacing the 501 stubs), approvals inbox and confirm UI, policy-change display (source-supplied), enrollment flow, audit + `desktop`/`command` notifications, docs with the residual-risk statement.

## Slice 14 — Android daemon in Termux (durable repo; additional platform target)

- **Observable outcome:** on a real Android phone, `termux/bootstrap.sh` (idempotent) installs Node, git, gh, Pi and the durable app in Termux; `durable doctor` shows `os: android`, `service: termux-runit`, `dispatcher: git-process`, `tailscaleCli: false`, `peerCheck: optional`; an agent runs under `termux-services` with a wake lock, survives a kill (pi-durable resume) and a Termux restart via Termux:Boot; the console (slice 11) lists it, shows `offline` when the phone sleeps or Termux is killed, and `online` again after; the agent runs steward + scout + chat and one light **durable-conversation** worker (the Android default kind, git-process providing only the worktree) producing a draft PR on a small repo; a lease taken by the phone expires and another machine takes over when the phone vanishes mid-claim; auto-merge is refused by doctor.
- **Revision 7:** the Android default worker kind is **`durable-conversation`** (headless, no extra process, no TUI, no skills-repo dependency, token not in the shell; `maxConcurrent: 1`; `git-process` only provides the git worktree). Pi-session workers remain an opt-in on Android, and `idea-to-pr` workflows run on desktop machines.
- **Layers:** `platform/service/termuxRunit.ts`, `platform/notifier/termuxNotification.ts` (non-nonce-safe), `termux/bootstrap.sh` + runit templates, capability handling in doctor and the console (no Orca checks, peer check `unavailable (optional)`), tailnet exposure per the spike's ranked options, Android defaults and conservative budgets, `docs` for the manual steps (F-Droid/GitHub build, Termux:Boot, battery optimization, wake lock, Termux private `$HOME`). The bootstrap lives in the durable repo, clones and pins durable directly and has no skills-repo dependency; worker skills are an optional, separately pinned input (without them `doctor` disables only the skill-dependent Pi-session roles; the default skill-free durable workers, steward, scout and chat need none). No cgroups under runit: the group + env-marker sweep (slice 3) is best-effort cleanup, so a hold on Android stays `holding`; stopping the steward alone does not establish exclusive ownership there and `/proc` cannot prove no future writer, so the operator must force-stop Termux or reboot before editing (`durable hold --verify` is advisory only).
- **Verification:** offline tests with stubbed `pkg`, `npm`, `sv`, `termux-*` and a temp `$PREFIX` (bootstrap twice, PL1-PL6 invariants); `ServiceManager` contract suite; live on a device using the slice 1 Android checklist results: kill and restart recovery, an overnight Doze run (tick gaps recorded), battery/thermal notes, a draft PR from a light worker, console online/offline transitions, claim-expiry takeover, token and profile separation.
- **Checkpoint:** user lives with the phone agent for several days, reviews battery cost and offline behaviour, and decides whether workers on the phone are worth keeping or the phone stays steward + scout + chat.
